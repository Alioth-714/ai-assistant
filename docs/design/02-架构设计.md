## 一、架构总览

系统采用**核心四层 + 支撑设施**的架构：

- **核心四层**：Layer 0 路由 → Layer 1 角色 → Layer 2 主协调者 → Layer 3 子 Agent
- **支撑设施**：Layer 4 工具层（文件操作、grep、git、网络等），不算入核心层数

## 三、多 Agent 协作流程

### 3.1 任务派发与认领

1. 主协调者拆解任务为子任务列表
2. **广播**任务描述到子 Agent 池
3. 子 Agent 根据自身 `capabilities` 匹配并**主动认领**
4. 主协调者确认派发（可拒绝不匹配的认领）
5. 未认领的子任务由主协调者**直接指派**剩余 Agent

> 协作机制（ADR 决策 2）：广播→认领→剩余再派

### 3.2 工作区共享

- 路径：`AI_ASSISTANT_DATA/workspace/{task_id}/`
- 格式：结构化 JSON
- 生命周期：任务创建时建、完成/取消时销毁，孤儿 24h 清理
- 用途：子 Agent 之间交换数据，避免直接通信

### 3.3 并发控制

- **写互斥**：同一文件同一时刻只允许一个 Agent 写（文件锁 JSON，见 `05-失败处理.md` §2）
- **显存调度**：3B 路由常驻 GPU、8B 主协调者内存驻留 + GPU 按需 offload；子 Agent 3B 并发上限 2（第 1 个 GPU、第 2 个 CPU），8B 子 Agent 走 CPU/云端；超出排队/降级
- **权威模型**：显存与并发调度以 `27-性能优化.md` 为唯一标准

- **格式**：结构化 JSON（人靠 AI 辅助编辑，前端表单或对话式生成）
- **注入方式**：启动时加载索引+摘要 → 运行时按需召回 → 主协调者过滤后注入子 Agent

- **外网策略**（决策 17）：常见文档站（docs.*/wiki.*/github.com）默认允许，提供开关可显式配置；其他域名首次访问询问

## 五、上下文管理

### 5.1 主协调者上下文

- 硬上限：8K token
- 正常情况：工作区数据外移，上下文只存指针
- 快满时：触发**摘要压缩**（保留关键决策和结论，外移详细数据）

### 5.2 子 Agent 上下文

- 3B 硬上限：4K token
- 8B 硬上限：8K token
- 超限处理：分段处理（跨文件重构时按文件拆分），增量 diff 模式
