# 05 - 失败处理

> 状态：已定稿 | 最后更新：2026-01-15 | 关联：02-架构设计.md、03-权限模型.md、21-更新与回滚.md、modules/07-主协调者.md、modules/10-工具层.md

## 一、概述

系统运行中可能遇到的失败类型：模型推理超时/崩溃、工具调用失败（文件不存在/权限不足）、网络请求失败（DNS/超时/拒绝）、文件操作冲突（并发写）、资源不足（显存/内存耗尽）、外部内容异常（格式错误/注入攻击）。

**核心处理原则**（决策 3）：
失败发生 → 按类型重试（见 §6.1）→ 检查原因 → 回滚已改 → 报告用户决定
纯文本
**禁止行为**：
- 自行降级到危险操作（如删除文件来释放空间）
- 静默忽略失败继续执行（可能导致数据不一致）
- 无限重试（浪费资源，加重系统负担）

**失败严重级别**：

| 级别 | 定义 | 响应方式 |
|------|------|---------|
| 低 | 非关键工具调用失败，有替代方案 | 记录日志，尝试替代，不影响主流程 |
| 中 | 子 Agent 执行失败，任务部分完成 | 按类型重试（§6.1）→ 回滚该子 Agent 已改 → 报告主协调者 |
| 高 | 主协调者自身错误、写操作失败导致数据不一致 | 立即回滚 → 保存现场 → 报告用户 → 等待指令 |
| 致命 | 系统级崩溃（Ollama 断连、磁盘满） | 保存状态 → 终止当前任务 → 提示用户重启 |

## 二、写操作互斥与文件锁

### 2.1 问题

多 Agent 协作时，两个子 Agent 可能同时尝试修改同一文件（如跨文件重构场景），导致内容覆盖或损坏。

### 2.2 解决方案：文件锁 JSON

- 锁目录：`AI_ASSISTANT_DATA/workspace/.locks/`
- 锁文件：`{file_path_hash}.lock.json`
- 锁内容：
json
{
"file_path": "/absolute/path/to/target.rs",
"holder": "sub_agent_3",
"task_id": "task_20260115_001",
"acquired_at": "2026-01-15T14:30:00+08:00",
"expires_at": "2026-01-15T14:35:00+08:00"
}
纯文本
### 2.3 锁获取流程
Agent 请求写文件 X
│
▼
检查 .locks/{hash(X)}.json 是否存在
│
├─ 不存在 → 创建锁文件 → 获取成功 → 执行写操作
│
└─ 存在 → 读取锁内容
│
├─ 已过期（expires_at < now）→ 删除旧锁 → 创建新锁 → 获取成功
│
└─ 未过期 → 检查持有者
│
├─ 是自己 → 续期（更新 expires_at）→ 继续执行
│
└─ 是其他 Agent → 返回错误 "FILE_LOCKED"
→ 主协调者决定：等待/重新派发/跳过
纯文本
### 2.4 锁释放

| 场景 | 处理方式 |
|------|---------|
| 正常完成 | 写操作结束后立即删除锁文件 |
| 异常退出 | 锁文件设置 5 分钟过期，超时自动释放 |
| 任务取消 | 主协调者主动清理该任务持有的所有锁 |
| 系统崩溃 | 启动时扫描过期锁（>5分钟）并清理 |

### 2.5 规则

| 规则 | 说明 |
|------|------|
| 同一文件同一时刻只有一个 Agent 可写 | 强制，由权限网关检查 |
| 读操作不需要锁 | 多个 Agent 可同时读 |
| 锁不可跨任务继承 | 任务结束必须释放 |
| 主协调者不受锁限制 | 主协调者可直接写（用于回滚/修复） |
| 锁文件本身并发保护 | 使用原子创建（Windows: CreateFile with CREATE_NEW） |

## 三、显存调度与并发上限

### 3.1 硬件约束

| 组件 | 规格 | 可用资源 |
|------|------|---------|
| GPU | RTX 2070 8GB GDDR6 | ~6.5GB 可用（系统保留 ~1.5GB） |
| CPU | i5-10400F | 6 核 12 线程 |
| 内存 | 16GB DDR4 | ~12GB 可用（系统占用 ~4GB） |

### 3.2 模型显存占用估算

| 模型 | 精度 | 显存占用 | 备注 |
|------|------|---------|------|
| Qwen2.5-3B | Q4_K_M | ~2.5GB | 路由层/轻量子Agent |
| Qwen2.5-7B | Q4_K_M | ~5.0GB | 主协调者/重活子Agent |
| 系统开销 | - | ~0.5GB | CUDA context 等 |

### 3.3 并发策略

**常驻模型**（权威模型见 `27-性能优化.md` §2）：
- Layer 0 路由（3B）：GPU 常驻，~2.5GB
- Layer 2 主协调者（7B）：内存常驻 + GPU 分层按需 offload（GPU 层保证余量 ≥ 1.5GB），GPU 占用 ≤ ~4GB
- 合计 GPU：~6.5GB → 正好用完可用显存，无冗余给第二个 GPU 子 Agent

**解决方案**：子 Agent 3B 第 1 个进 GPU（~2.5GB）、**第 2 个走 CPU 推理**；7B 子 Agent 不进 GPU（CPU 或云端）。通过 Ollama 的 `num_gpu` 参数控制各模型的 GPU 层数。

**子 Agent 并发上限**：

| 子 Agent 类型 | 单实例显存 | 最大并发数 | 超出时处理 |
|--------------|-----------|-----------|-----------|
| 3B 轻活 | ~2.5GB | 2（第 1 个 GPU、第 2 个 CPU） | 第 3 个排队（30s）→ 降级 CPU/云端/串行化 |
| 7B 重活 | ~5.0GB | 1（CPU 或云端，不进 GPU） | 与主协调者共享模型实例时排队 |
| 云端 | 0（本地） | 3 | 直接派发 |

**实际调度策略**：
1. 主协调者（7B）常驻，优先占用 GPU 资源（通过 Ollama `keep_alive`）
2. 子 Agent（3B）按需加载，使用完毕后立即卸载（`keep_alive=0`）
3. 当 GPU 显存不足时，新子 Agent 请求排队，最多等待 30 秒
4. 排队超时 → 主协调者决策：降级到云端 / 串行化执行 / 报告用户

### 3.4 内存保护

- 当系统内存使用超过 14GB（16GB 的 87.5%）时，拒绝新的子 Agent 派发
- 触发垃圾回收：清理已完成的任务工作区、过期缓存
- 极端情况：保存当前状态，提示用户关闭其他程序

## 四、Token 超限处理

### 4.1 硬上限

| 模型 | Token 上限 | 决策编号 |
|------|-----------|---------|
| 3B（路由/轻活） | 4K | 决策 8 |
| 7B（主协调者/重活） | 8K | 决策 8 |

### 4.2 超限检测与响应
上下文构建时
│
▼
估算当前 token 数
│
├─ < 70% 上限 → 正常继续
│
├─ 70%-90% → 触发预警
│ → 主协调者：开始外移详细数据到工作区，上下文只保留指针
│ → 子 Agent：提醒主协调者减少注入数据量
│
├─ 90%-100% → 触发摘要压缩
│ → 保留：用户最新指令、关键决策、待执行任务
│ → 压缩：历史对话、详细数据、中间结果
│ → 外移：大段代码/文档移至工作区文件，用指针引用
│
└─ > 100% → 硬截断 + 警告
→ 截断最早的非关键内容
→ 记录警告到日志
→ 通知用户"上下文已截断，可能影响连续性"
纯文本
### 4.3 8K 上限 vs 重构任务

跨文件重构时，单个文件可能就超过 8K token。处理策略：

| 策略 | 说明 |
|------|------|
| 分段处理 | 按文件拆分任务，每个子 Agent 只处理一个文件 |
| 增量 diff | 子 Agent 返回 diff 而非完整文件，减少 token 消耗 |
| 文件指针 | 上下文只存文件路径+关键行号，详细内容从磁盘读取 |
| 摘要传递 | 跨文件依赖关系用摘要描述，不全量注入 |

### 4.4 子 Agent 上下文隔离

- 子 Agent 上下文独立于主协调者
- 主协调者向子 Agent 注入数据时，只给**任务必需的最小数据集**
- 注入前检查数据量，超过子 Agent 上限的 70% 时自动分段或外移

## 五、Prompt 注入防护

### 5.1 威胁模型

外部内容（网页抓取、文档导入）可能包含恶意指令，试图：
- 覆盖系统 prompt
- 泄露上下文中的敏感信息
- 诱导执行危险操作

### 5.2 防护措施

| 措施 | 说明 |
|------|------|
| 数据标记 | 外部内容注入时添加 `[EXTERNAL: {url}]` 前缀，明确标识来源 |
| 指令过滤 | 检测 `system:`、`ignore previous`、`do anything` 等指令关键词，命中则警告并截断 |
| 上下文隔离 | 外部内容只作为"数据"注入，不作为"指令"；子 Agent 上下文与主协调者上下文分离 |
| 输出审查 | 子 Agent 返回结果中若包含疑似指令模式，主协调者审查后再展示给用户 |
| 权限限制 | 外部内容触发的操作仍受权限网关约束（L2 需确认） |

### 5.3 多模态安全

- 图片理解：遇到图片需多模态理解时，询问用户"传云端分析还是跳过？"（决策 18）
- 敏感图片：不自动上传，用户显式确认后才传输

## 六、失败重试与回滚

### 6.1 重试策略

| 失败类型 | 重试次数 | 重试间隔 | 备注 |
|---------|---------|---------|------|
| 模型推理超时 | 2 | 固定 2s | Ollama 可能临时过载 |
| 文件锁冲突 | 5 | 固定 500ms | 等待锁释放 |
| 网络请求失败 | 3 | 指数 1s/2s/4s | DNS/临时网络抖动 |
| 工具调用参数错误 | 0 | - | 返回主协调者重新规划 |
| Git 操作冲突 | 0 | - | 需用户介入解决 |
| 权限拒绝 / 配置错误 | 0 | - | 不重试，直接报告 |

### 6.2 回滚流程
失败确认（类型级重试后仍失败）
│
▼
检查是否有已执行的写操作
│
├─ 无写操作 → 直接报告用户
│
└─ 有写操作 → 触发回滚
│
▼
从 AI_ASSISTANT_DATA/backups/ 恢复备份
│
├─ 备份存在 → 恢复文件 → 验证恢复结果
│
└─ 备份不存在 → 记录错误 → 报告用户（需手动修复）
│
▼
回滚结果报告
· 成功：告知用户已恢复，询问是否继续
· 失败：告知用户回滚失败，提供备份路径，建议手动恢复
纯文本
### 6.3 回滚范围

| 操作类型 | 回滚方式 |
|---------|---------|
| 单文件修改 | 从 backups/ 恢复该文件 |
| 多文件修改 | 按修改顺序逆序恢复 |
| 配置变更 | 从 config/ 的版本历史恢复（如有） |
| 知识库更新 | 从知识库 JSON 的 `_previous` 字段恢复 |
| Git 操作 | `git reset --hard`（仅限 Agent 创建的 commit） |

## 七、子 Agent 失败处理

### 7.1 子 Agent 异常退出

| 场景 | 处理 |
|------|------|
| 子 Agent 进程崩溃 | 主协调者检测到无响应 → 标记任务失败 → 触发重试或重新派发 |
| 子 Agent 返回格式错误 | 解析失败 → 重试 1 次（子 Agent 级兜底）→ 仍失败则报告用户 |
| 子 Agent 超时（>5分钟） | 强制终止 → 清理资源 → 报告用户 |
| 子 Agent 上下文溢出 | 通知主协调者 → 主协调者减少注入数据 → 重新派发 |

### 7.2 子 Agent 失败对主流程的影响

| 情况 | 影响 | 主协调者决策 |
|------|------|-------------|
| 非关键子任务失败 | 主流程可继续 | 记录失败，用替代方案或跳过 |
| 关键子任务失败 | 主流程阻塞 | 重试 → 回滚 → 报告用户 |
| 多个子 Agent 级联失败 | 系统不稳定 | 暂停所有任务 → 保存状态 → 报告用户 |

## 八、用户感知与报告

### 8.1 默认静默（决策 5）

- 轻量级失败（工具调用重试成功）：不打扰用户，只记录日志
- 中等失败：任务完成后在摘要中提及"部分操作失败但已自动恢复"

### 8.2 需要用户介入

| 场景 | 用户提示 |
|------|---------|
| 类型级重试后仍失败 | "操作失败，已尝试自动恢复。是否手动处理？[是/否]" |
| 回滚失败 | "自动回滚失败，备份位于 {path}，请手动恢复。" |
| 权限被拒绝 | "操作被权限网关阻止，是否允许？[允许/拒绝]" |
| 显存不足 | "GPU 资源不足，是否切换到云端执行？[是/否/取消]" |
| 外部内容含可疑指令 | "检测到外部内容可能包含恶意指令，已拦截。是否强制加载？[是/否]" |

### 8.3 报告格式
