## Ollama 集成（决策 22）

使用 `ollama-rs` crate 封装 Ollama HTTP API。

### 连接

```rust
use ollama_rs::Ollama;

let ollama = Ollama::new("http://localhost".to_string(), 11434);
```

### Chat

```rust
use ollama_rs::generation::chat::{ChatMessage, ChatRequest};

let messages = vec![
    ChatMessage::system("你是一个助手".to_string()),
    ChatMessage::user("你好".to_string()),
];

let res = ollama.send_chat_messages(ChatRequest::new(
    "qwen25-7b".to_string(),
    messages,
)).await?;
```

### 工具调用

qwen2.5 系列支持 Ollama 原生工具调用（`tools` 参数）；早期版本也可用 prompt 约定格式的伪 tool_use：

```
用户输入 → 模型返回 → 检测是否有 <function=xxx> 标记
  → 有 → 解析参数 → 调工具 → 结果回注 → 继续
  → 无 → 直接输出
```

## 模型池与档位（模型策略，B+D）

**策略要点**：

- **角色声明档位，不写死模型**：角色 YAML 只写 `model_preference: light | heavy | cloud`（见 `modules/11-角色切换.md`）；具体模型由下表（环境映射）决定。换机 / 升级 / 换模型 → 只改映射表，角色与人设不动（模型纯净原则）。
- **最小模型集先跑通**：初期仅 light + heavy 两档本地模型 + cloud 兜底，**不给每个角色单独配模型**。某角色某类任务持续拉垮且轻/重档救不了时，再按别扭点数据给它特化模型（如 general 角色可选 `qwen25-7b` 通用版）。
- 其余文档中「7B 主协调者 / 7B 子 Agent」均指 **heavy 档**，具体模型以本表为准。

| 档位 | 默认模型 | 显存 | 调度方式 |
|------|---------|------|---------|
| light | qwen25-3b | ~2.5GB | GPU 常驻（路由层 + 轻活子 Agent） |
| heavy | qwen25-7b (Q4_K_M) | ~5.0GB | 主协调者：内存常驻 + GPU 分层 offload（GPU ≤ ~4GB）；重活子 Agent：CPU 或云端，不进 GPU |
| cloud | deepseek-chat（兜底） | - | 云端，仅脱敏描述 + 用户确认（决策 18/27）；启用时机按 `roadmap/18` 能力边界 |

> **角色区分（重要）——运行时大脑 = 唯一大脑（2026-10-22 起）**：
> - **大脑 = `qwen25-7b`（通用 7B，heavy 档）**：运行时主协调者默认（设计如此），**唯一大脑**。阶段 0 实测它在 **Cline（开发工具场景）** 里做 agent 任务会循环调用同一工具、文件写到一半截断——这只说明它**不适合开发期 Cline 编排**，**不等于运行时大脑不行**；运行时表现已实测（`roadmap/17` §阶段 2 / test.sh）：单步可靠、0 循环，但多步工具链必挂、改文件有截断波动（详见 `roadmap/18` §二）。
> - ~~**开发工具 = `qwen3:8b`**~~ **已移除（2026-10-22）**：用户决定显卡有限、运行时只保留 7B 一个大脑，不来回切模型（该档位原用于 Cline / 开发期，原生 `tool_calls` 可靠）。Cline 等开发期载体如需独立模型，另行评估（见 `ops/13-Cline集成.md`）。
> - `qwen25-7b` 同时保留 general 角色数据驱动特化的候选位置。

RTX 2070 8GB 上：light 路由（2.5GB）+ heavy 主协调者分层（~4GB）≈ 6.5GB，正好用尽可用显存；因此**子 Agent 第 2 个走 CPU、重活子 Agent 走 CPU/云端**（见 `27-性能优化.md` §2.3）。

## 模型管理

### 模型发现与扫描

- 扫描本地 Ollama 已拉取模型列表（`ollama list`）+ 扫描本地 GGUF 源目录（默认 `{程序目录}/models/`，递归深度 ≤ 5 层）
- 程序**不直接加载 GGUF**（架构：程序 → Ollama API → 模型推理），GGUF 需先 `ollama create` / `ollama import` 进 Ollama
- 用户可从**任意路径**导入 GGUF（见「模型根目录」，路径可配置），导入逻辑不依赖默认目录
- 扫描结果缓存到 `AI_ASSISTANT_DATA/cache/models.json`

### 模型根目录

- 本地 GGUF 源目录默认 = `{程序目录}/models/`（工程内置，下载的 本地模型组合 放这里）
- 可用环境变量 `AI_ASSISTANT_MODELS`，或 `config/models.json` 的 `models_dir` 字段，改为任意路径（如 `D:\models`）；改动后默认目录依然保留，导入/扫描逻辑不变
- Ollama 实际模型存储（导入后）在 `~/.ollama/models/`，不受上述配置影响

### 模型纯净原则（人设不入模型）

- 核心模型（路由 / 主协调者 / 子 Agent）一律使用**干净基底**（GGUF 不含人设/系统提示）
- 禁止通过 `Modelfile` 的 `SYSTEM` 给核心模型写入人设；`ollama show <model>` 的 System 字段应为空或仅通用默认
- 人设/系统提示词由**配置层**提供：dev 角色 = `docs/agent.md`；扩展角色 = 角色 YAML 的 `prompt:` 字段（见 `modules/11-角色切换.md`）
- 由此保证：**换模型 / 改模型路径 / 从别处导入 → 人设不变**（人设随配置走，不随模型走）
- 校验：注册模型后 `ollama show <model>`，确认 System 无角色人设

### 模型分配与切换

- 首次启动检测模型是否已拉取；未拉取 → 提示用户 `ollama pull qwen25-3b`（light）/ `ollama pull qwen25-7b`（heavy）
- 设置界面可把某个模型分配给「light / heavy / cloud」档位，写回 `config/models.json`（角色 YAML 只声明档位，不写具体模型）
- 切换后校验显存可行性（按 27 §2.2 估算），超限给出警告

## 云端兜底（决策 27）

云端 = 用户配置的 **OpenAI 兼容接口**（平台名 + Key + 模型），仅作本地模型兜底。启用时机按 `roadmap/18-本地云端边界方案.md`：读/检索/工具永远本地，仅「生成」环节在本地不足时上云（脱敏 + 用户确认）；阶段 0-2 以本地为主，未配置 Key 时恒为纯本地。

配置（Key 存 `config/secrets.json`，阶段 3+ 加密；平台/模型名可在设置界面改）：

```json
{
  "cloud": {
    "_comment": "云端兜底：OpenAI 兼容平台名+Key（阶段3+启用）",
    "enabled": false,
    "provider": "deepseek",
    "base_url": "https://api.deepseek.com/v1",
    "api_key": "sk-xxxx",
    "chat_model": "deepseek-chat",
    "vision_model": "deepseek-vl"
  }
}
```

三条规则：

- ① 开了才用：`enabled: true` 才启用，否则纯本地；未配置 Key 时恒为纯本地（本地不足的难点转「能力不足」提示，见 `roadmap/18`）
- ② 发前脱敏：去路径/密钥/内网地址，只发描述（见 `04-数据边界.md`）
- ③ 传图先问：图片多模态走云端需用户确认（决策 18）

其他：本地模型失败 / 排队超时 / 重活 7B 不够 → 可降级云端；云端失败 → 降级本地并报告用户。
