## 一、为什么需要这份方案（背景）

阶段 2 大脑实测（`test.sh`，见 `roadmap/17-阶段Demo执行计划.md` §阶段 2）首次把「运行时大脑能不能做多步工具编排」从假设变成了数据。结论是：**本地 7B/8B Q4 的硬边界 = 多步工具链**，而这正是主协调者（大脑）的核心工作。

因此「本地/联网的边界」不再是想当然，必须显式定下来。本文档给出：

- **事实依据**：阶段 2 实测结论
- **铁律**：哪些环节永远不出网
- **能力边界表**：三个核心场景（资料总结 / 代码分析 / 本地工作流）的子任务粒度归属
- **边界设计三方案** + 推荐
- **升级上云的判定规则**
- **B+D 落地映射**

## 二、阶段 2 大脑实测结论（事实依据）

用 `test.sh` 对 qwen25-7b（大脑·heavy）与 qwen3:8b（开发工具·dev）跑三层验证（裸测 / 工具协议 / 端到端 5 用例）。实测结果：

| 能力 | qwen25-7b | qwen3:8b | 判定 |
|---|---|---|---|
| 原生 `tool_calls` 协议 | ✅ | ✅ | 自研可直接按原生格式解析 |
| 单步：读+总结 / 读不存在如实报错 / 逻辑一致 | ✅ | ✅ | 可靠 |
| 单步改文件（读→写全文） | ⚠️ 波动（一次未读直接写、内容截断成 15 字符） | ✅ 稳定 | qwen3:8b 更稳 |
| **多步工具链**（读到内容→下一步写入） | ❌ 写占位符 `${read_file.return}` | ❌ 直接丢内容只写 `#END_MARKER` | **两模型 100% 失败，硬边界** |
| 循环 | 0 | 0 | 单步场景不触发（不代表多步安全） |

**三条硬结论**：

1. **单步工具调用可靠、零循环** → 本地能胜任「看当前状态 → 发一个工具调用」。
2. **多步工具链必挂** → 本地不能胜任「记住上一个工具结果并拼进下一步」。
3. **反直觉信号**：qwen3:8b 工具执行比 qwen25-7b 稳（case2 稳定先读后写；qwen25-7b 出现未读直接写+截断）。单样本有波动，需更多样本确认，但指向 8B 工具执行更稳。

> **核心启示**：多步链的失败不是模型「不会调工具」，而是模型「扛不住跨步骤的状态传递」。这个责任应交给**代码**，而不是换个更大的本地模型硬扛（7B→8B 没解决，8B 换 14B 也只是缓解概率）。

## 三、铁律：读与检索永远本地

**只有「生成/推理」这一步才可能出网，且云端只兜「本地做不好」的那一截。**

| 环节 | 归属 | 理由 |
|---|---|---|
| 文档解析（纯文本/md/docx） | 🟢 本地工具 | 确定性，无模型 |
| 分块 + 向量化 + 检索 | 🟢 本地 | nomic-embed-text 本地又便宜又快 |
| 工具执行（读写文件/命令/搜索） | 🟢 本地 | 确定性代码 |
| 意图路由 / 角色分发 | 🟢 本地 3B | <2s，已验证 |
| 单步生成（短摘要/改写/答小问题/单步决策） | 🟢 本地 7B/8B | 实测可靠 |
| **难生成 / 高质量 / 长上下文推理** | 🔴 云端兜底 | 本地 Q4 能力上限 |

## 四、能力边界表（三个核心场景）

### 4.1 资料总结（本地+云混合**最重**的场景）

| 子任务 | 归属 | 说明 |
|---|---|---|
| 文档解析（纯文本/md/docx） | 🟢 本地工具 | 确定性 |
| 分块 + 向量化 + 检索 | 🟢 本地 | embedding 本地 |
| 扫描版 PDF 的 OCR | 🟡 边界点 | 本地需下 OCR 模型+开发量；云端现成 API |
| 短文档 / 单段落摘要 | 🟢 本地 7B | 够用 |
| 长文档「分块逐步摘要」（map-reduce） | 🟢 本地（代码编排） | 每步单步，符合 A 方案 |
| **跨段落深层总结 / 提炼观点** | 🔴 云端 | 7B 会丢重点、泛泛而谈 |
| 最终润色 / 高质输出 | 🔴 云端（可选） | 用户要「高质量」时 |

> ⚠️ 「总结质量」是本地 7B 最弱的一项，恰是三个场景里排第一的。短文档本地 OK，长/专业文档默认上云。

### 4.2 代码分析（本地工具做「读+结构」，推理要云）

| 子任务 | 归属 | 说明 |
|---|---|---|
| 读文件 / 搜索 / 语法树 / 依赖图 | 🟢 本地工具 | tree-sitter、grep，确定性 |
| 函数级解释 / 注释 / 命名建议 | 🟢 本地 | 7B/8B 尚可；**coder 模型更强** |
| 单文件简单 bug 定位 | 🟡 本地先试 | 行内小错能抓 |
| **跨文件重构建议 / 架构级分析** | 🔴 云端 | 需长上下文+强推理 |
| **安全审查 / 复杂 bug 定位** | 🔴 云端 | 7B 会漏报/误报 |

> 关键洞察：代码分析是「读多写少」，本地工具能把「读+结构」做到位，但「理解全局+给建议」的**生成步**要靠云。

### 4.3 本地工作流（A 方案主场，大部分本地）

| 子任务 | 归属 | 说明 |
|---|---|---|
| 意图路由 / 角色分发 | 🟢 本地 3B | <2s，已验证 |
| 预设模板工作流（代码编排+单步决策） | 🟢 本地 | **A 方案实锤可行** |
| 确定性工具执行（读写/命令/定时） | 🟢 本地 | 纯代码 |
| 简单条件分支 | 🟢 本地 | 代码/3B |
| **自然语言复杂任务拆解（开放式）** | 🔴 云端 | 本地多步链必挂（实锤） |
| 长流程、边执行边调整重规划 | 🔴 云端 | 同上 |

## 五、边界设计三方案利弊

### 方案①：静态白名单（按任务类型一刀切）

- **好处**：最简单、边界可预期、成本好控制、好测试、隐私承诺一句话讲清。
- **坏处**：粒度太粗——同一个「总结」，3 行摘要本地够、30 页白皮书本地不够，静态分不开；容易「浪费地出网」或「硬撑本地质量差」。

### 方案②：动态置信度升级（本地先试→失败再云）

- **好处**：隐私最大化（能本地就不出网）、成本最低、自动适配难度、本地响应快。
- **坏处**：**「何时算不行」极难判断**——7B 自评置信度不可靠，只能靠外部信号（重试/校验失败）；用户不知道这次会不会出网，**隐私承诺讲不清**（违背「诚实」准则）；本地失败再上云的延迟叠加。

### 方案③：混合（静态默认 + 动态升级 + 用户开关）✅ 推荐

- **好处**：取两者之长；**「用户开关」把隐私最终决定权交还用户**（接上 `design/04` 既有的「用户显式确认」机制）；**直接复用 B+D 的 `model_preference: light|heavy|cloud` 分级机制**，不推翻任何设计——每个能力注册一个默认 grade，运行时按 grade 路由 + 动态信号微调。
- **坏处**：实现量最大（白名单 + 升级规则 + 开关三套），但可渐进：阶段 0-1 先上静态白名单，动态/开关阶段 2+ 补。

## 六、升级上云的判定规则（可落地）

1. **静态白名单**（定死，现在就能定）：命中「架构级代码分析 / 长文档高质量总结 / 开放式多步规划」→ 直接上云。
2. **动态信号降级**（本地先试，超阈值再云）：
   - 本地输出校验失败（格式错 / 占位符 / 空输出）→ 上云
   - 单步重试 ≥2 次仍不行 → 上云
   - 上下文超限（文档太长，截断会丢信息）→ 上云
3. **用户显式开关**：每次出网前**明确提示「这一步将联网」**，用户可一键「仅本地」或「我要高质量（上云）」。

## 七、B+D 落地映射

把「能力 → grade」做成一张表，每个能力标注 `local / local-first / cloud`，运行时按 grade 路由。

建议新增**可维护配置**（类比 `config/models.json`）：`config/capabilities.json`，把第四节的三张表落成一个数据文件，而不是写死进代码：

```json
{
  "_comment": "能力边界：grade 取值 local(纯本地) / local-first(本地优先可升级) / cloud(默认云端兜底)",
  "capabilities": {
    "summarize_short":   { "grade": "local",        "note": "短文档/单段落摘要" },
    "summarize_long":    { "grade": "cloud",        "note": "长文档跨段落深层总结" },
    "code_explain_local":{ "grade": "local",        "note": "函数级解释/注释" },
    "code_refactor":     { "grade": "cloud",        "note": "跨文件重构/架构分析" },
    "workflow_templated":{ "grade": "local",        "note": "预设模板工作流(代码编排+单步决策)" },
    "workflow_open_plan":{ "grade": "cloud",        "note": "开放式多步任务拆解" },
    "ocr_scanned_pdf":   { "grade": "local-first",  "note": "先本地OCR，失败上云" }
  }
}
```

> 阶段 0-1 先跑 `local` 和 `cloud` 两级；`local-first`（动态信号）和「用户开关」到阶段 2+ 再接。这样「本地/联网边界」从第一天就是**显式可审计**的，而不是藏在代码里。

## 八、风险与诚实提醒

1. **边界不是一次性定死的**：会随「本地模型升级（如换 14B）」和「实测质量阈值」动态漂移。这就是为什么要用 `capabilities.json` 可维护配置，而非写死进文档/代码。
2. **本地总结质量是短板**：资料总结（用户第一场景）正是本地最弱、不得不大量走云的部分，要有预期。
3. **qwen25-7b 多步链 + 改文件波动**：若阶段 1 实测持续不稳定，大脑（heavy）档应考虑换 qwen3:8b 或更大模型——本方案不锁定具体大脑模型。
4. **云端兜底≠推翻本地优先**：出网只发生在「生成」这一小步、且按第三节铁律最小化；「读/检索/工具」永远本地。

## 九、决策与待决事项

- **已定**：B 方案（换 14B 硬扛）**不选**；采用 **A+C 折中**（代码编排为主 + 云端兜底）。
- **已定**：边界设计用**方案③混合**（静态白名单 + 动态升级 + 用户开关）。
- **待用户拍板**：`capabilities.json` 的粒度、云平台选型（deepseek-chat 占位）、「联网前提示」的交互形态。
