# 18 - 能力分层与本地/云端对接方案

## 一、为什么改（背景）

阶段 2 实测确认：本地 7B Q4 的**多步工具链 100% 失败**（写占位符/丢内容），长文档总结、架构级分析是本地最弱项。实践反馈一致——**3B+7B 做复杂任务不现实**。

原方案「本地优先，云端兜底」的问题不是方向错，而是**默认值反了**：认知复杂度超限的任务会先让本地撞一次墙（失败+回滚+再上云），既慢又留下垃圾输出。

**新理念（决策 33）**：

> 3B+7B 阶段：本地负责简单工作与**编排类**工作，认知复杂的任务**默认对接云端**；
> 升级到 14B+ 后：本地承担更多，云端只在少数情况兜底；
> 32B 阶段：目标是**离线可完成绝大部分日常任务**（不是"零云依赖"）。

## 二、关键区分：两种「复杂」（本方案的地基）

| 类型 | 例子 | 本地能否胜任 | 归属 |
|---|---|---|---|
| **编排复杂**（多步/多文件） | "读这 5 个文件，各自提取要点再汇总" | **能**——每步单步简单，代码拼接即可（Planner + Tool Guard 已实现） | 本地 |
| **认知复杂**（长上下文理解/深度推理/高质量写作） | "分析整个架构并给出重构方案" | 不能——超出 7B 推理与上下文预算 | 云端 |

**按认知复杂度分档，而不是按"步骤多不多"。** 把"读 5 个文件汇总"推给云端，等于花 5 倍钱、5 倍延迟、送出 5 份文件内容，换 Planner 本来就能给的收益。

## 三、三档能力（grade）

| 档 | 判定 | 行为 |
|---|---|---|
| **local** | 读写文件、单文件改动、短摘要、意图路由、模板工作流 | **永不出网** |
| **localFirst** | 单文件 bug 定位、函数级解释、中等摘要、OCR | 本地先试 → 校验失败/重试≥2/上下文超限才升级 |
| **cloud** | 长文档高质量总结、跨文件重构、架构级分析、开放式多步规划 | **默认直接上云**（不再本地先撞墙） |

与旧方案的差别只有一句：**cloud 档从「例外兜底」变成「一等公民」**；local / localFirst 机制原样保留。

## 四、判定优先级（谁判"复杂"）

1. **用户「仅本地」开关**（最高，默认开启）
2. **静态能力白名单**（`config/capabilities.json`，确定性）
3. **确定性信号**：文件数 ≥2 或输入 >8000 字符 → 升一档
4. **模型自评**：**不参与决策**（阶段 2 已证明 7B 自评不可靠），最多作为提示文案

## 五、profile 机制（换硬件只改配置）

`config/capabilities.json` 里 `profile: small | large`，同一份能力表两套映射：

| 能力 | profile=small（3B+7B） | profile=large（14B+） |
|---|---|---|
| summarize_long | cloud | local |
| code_refactor | cloud | localFirst |
| workflow_open_plan | cloud | localFirst |
| code_explain / read_write_file / summarize_short | local / localFirst | local |

**硬件门槛（诚实数字）**：

| 模型 | Q4_K_M 权重 | 需要的显存 | 结论 |
|---|---|---|---|
| 7B | ~4.4GB | 8GB 可分层跑 | 现状 |
| 14B | **~8.5-9GB** | **≥12GB**（3060 12G / 4070 12G），16GB 更稳 | small→large 的门槛 |
| 32B | **~19GB** | **≥24GB**（3090/4090） | 终极目标阶段 |

**切换判据**：先跑**硬件基准**（显存占用、首 token、吞吐），再跑**任务基准**（10-20 条典型任务通过率），两项达标才切 `large`。不达标就切 = 自欺。

## 六、云端交互（「仅本地」开关）

沟通栏下方「仅本地」按钮，**默认开启**（安全默认，启动即此态）：

| 开关 | 行为 |
|---|---|
| **开启（仅本地）** | 只跑本地模型；遇到 cloud 档能力时**弹窗每次放权**；用户不批 → 本地降级执行并说明质量受限 |
| **关闭（自动）** | 复杂任务经**本地确定性抽取**后直接上云，**不弹窗** |

不做静默的部分（避免"忘了开关"导致外泄）：

- 关闭开关时给一次**强提示**（"此后复杂任务将直接使用云端，敏感内容仍受红线保护"）
- 状态栏常驻显示当前模式 + 本次会话云端次数
- 每次出网写**审计条目**（时间、能力档、内容摘要、是否放权）
- **会话云端预算上限**（默认 50,000 tokens）：超额自动降级为仅本地，并提示提高上限

**消息流不标注"本地/云端"**（用户决定：会显得杂乱）；可见性靠**状态栏模式 + 云端计数**与**审计日志**保证。

## 七、隐私红线（不可协商）

**敏感内容即使「仅本地」开关关闭、即使有导出授权，也绝不上云。**

**红线清单**（`src/egress.rs` 实现，与 `tools.rs` 的读取拦截互补）：

- 文件名：`secrets.json`、`credentials*`、`.env*`、`id_rsa` / `id_ed25519` / `id_ecdsa`、`.netrc`
- 扩展名：`.key`、`.pem`、`.p12`、`.pfx`、`.jks`、`.keystore`
- 目录：`.ssh`、`.aws`、`.gnupg`
- 内容形态（兜底层）：`sk-…`、`-----BEGIN … PRIVATE KEY-----`、`AKIA…`、`ghp_…`、`xox…-`、`AIza…`

**程序不得代为搬运**：命中红线时只**拦截并提示**，不读取、不复制、不代传；界面只提供"查看方法"（打开文件/复制路径），由用户自己去对应位置复制。用户手动粘贴后，程序无法判断来源，此时靠**密钥形态检测**兜底并警告，责任转移给用户。

**两层防护**：

1. **来源标记（可靠层）**：工具读取时按路径打 `sensitive_source` 标记 → 出网闸门据此拦截
2. **形态检测（兜底层）**：手抄内容也能识别

**出网统一入口**：复用已有 `ExportGate`（授权确认）+ 新增 `egress::inspect`（红线检查）双闸门，先红线、后授权。

## 八、本地"初步处理"= 确定性抽取（不是让 7B 摘要）

自动模式关闭开关后，复杂任务上云前由本地做的**初步处理**必须是确定性手段：

- 文件树 / 目录结构
- 符号表（函数、类型、模块名）
- `grep` 命中行
- 代码块提取 / 结构化标题层级
- 长度与规模统计

**不**让 7B 做摘要再上云：7B 摘要在 8K 内会截断丢重点，且摘要本身也占 token，质量与成本双输。

## 九、实现映射（已落地）

| 组件 | 位置 | 职责 |
|---|---|---|
| 能力表 | `config/capabilities.json` | grade 白名单 + small/large 两套 profile |

| 路由接线 | `src/runtime.rs` | `route_decision()` 决定档位；`send_external_message` 前置红线+预算检查 |
| 前端开关 | `frontend/index.html` + `js/app.js` + `css/style.css` | 沟通栏左下「仅本地 / 自动·云端」按钮（默认仅本地）；关闭时强提示确认；状态栏显示模式与云端次数 |

| 本地编排 | `src/planner.rs` + `src/guard.rs` | 编排复杂任务由本地代码拼接完成（决策 31/32）；**已接入运行时**：`auto_template` 命中「单路径 + 总结意图」即走 Planner（读 → 单步总结），未命中才回落 orchestrator / coordinator；工具层带**单轮循环守卫**（同参 ≥3 次拦截） |

## 十、推理层优化借鉴（DeepInfer 参考）

DeepInfer（DeepSeek 2026-10 开源，Apache 2.0，基于 vLLM）**不能直接用**：要求 SM100/昇腾 950，明确不支持消费级卡；面向 DeepSeek MoE 大模型的离线批量推理。**只能借思路**：

**现在就能做（已落地）**

| 借鉴点 | 落地 | 效果 |
|---|---|---|
| 结构化输出（json_schema） | 路由/拆解用 JSON Schema 约束 | 消掉"解析失败→重试"循环（实测 HTTP 200 通过） |
| SWA Bounded Replay → 前缀稳定 | system 提示常量前置、长期记忆后置 | 命中 prompt cache（响应可见 `prompt_eval_cached_count`） |
| 确定性推理 | `ChatOptions::deterministic()` + `config.testing.deterministic` + 固定 seed 42 | 测试/验收可复现 |
| 编解码集中（deepseek-recipe 哲学） | `src/render.rs` 收敛截断/tool_calls 归一化/JSON 抽取 | 换模型行为一致 |
| 上下文按角色分档 | 路由 2048（输入截 1200 字符）、大脑 8192 | KV cache 减半，首 token 更快 |

**换 12GB+ 卡后值得试**：投机解码（3B 当 draft、7B 当 target）。8GB 卡别试——3B+7B 权重已 6.4GB，draft 还要 KV，会挤爆反而更慢。

**不做**：MoE EP/EPLB、FlashMLA/DeepGEMM（dense 模型用不上）、Prefill/Decode 分离（单机无意义）、换掉 Ollama 上 vLLM（需重写适配层，先把 Ollama 参数榨干）。

## 十一、风险与诚实提醒

1. **隐私面扩大**：cloud 档默认上云，复杂任务恰是最可能含敏感代码/文档的。红线与预算机制是补偿，但无法覆盖"用户手动粘贴"的场景。
2. **成本与延迟常态化**：cloud 档不再是例外，预算上限是唯一刹车。
3. **离线降级**：断网只能做 local 档；必须明确提示质量受限，不静默失败。
4. **14B 的期望管理**：14B Q4 约 GPT-3.5 水平，架构级推理仍明显弱于云端前沿模型。"14B 时极少外接"偏乐观，**建议表述为"少部分外接"**。
5. **profile 判定不能拍脑袋**：必须硬件基准 + 任务基准双达标，否则切了也是自欺。

## 十二、决策与待决

- **已定**：按认知复杂度分档；cloud 档为一等公民；profile small/large 机制；「仅本地」默认开启、关闭时不弹窗但保留强提示/审计/预算；隐私红线程序不代搬运；本地初步处理用确定性抽取；profile 判据"先硬件后任务"。
- **已定**：B 方案（换 14B 硬扛多步链）不选；A+C 折中保留（代码编排 + 云端兜底）。
- **待拍板**：`capabilities.json` 的能力粒度是否再细分；云端模型选型（现占位 deepseek-chat）；「仅本地」开关在 UI 上的具体形态（图标/文案）。
